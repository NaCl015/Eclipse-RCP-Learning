# 开始用 Eclipse 之前：概念入门

> 目标：在你点开 Eclipse 之前，先建立一张“地图”，知道每个安装项、每个名词、每次点击背后发生了什么。
> 配套文档：[01-学习路线图](01-学习路线图.md)、[02-软件安装与配置清单](02-软件安装与配置清单.md)、[04-本次安装手册](04-本次安装手册.md)、[05-Eclipse三层架构详解](05-Eclipse三层架构详解.md)

## 一、一句话总览

**Eclipse RCP = 用 Eclipse 的“插件运行时 + 桌面框架”，组装你自己的桌面应用。**

你学的不只是“用 Eclipse 这个编辑器”，而是：

- Eclipse 的**模块化机制**（OSGi）；
- Eclipse 的**扩展机制**（插件 + 扩展点）；
- Eclipse 的**桌面框架**（SWT/JFace/e4 Workbench）；
- Eclipse 的**交付机制**（Feature/Product/p2/Tycho）。

这四样东西合起来，才叫 RCP 开发。

## 二、Eclipse 到底是什么

很多人以为 Eclipse 是一个“写 Java 的 IDE”。这只说对了一半。

Eclipse 至少有三层：

```text
┌─────────────────────────────────────────────┐
│ 3. IDE 工具层                                │
│    JDT（Java 编辑器/编译器）、PDE、Git、Maven │
├─────────────────────────────────────────────┤
│ 2. 桌面应用框架层                            │
│    Workbench、e4 应用模型、SWT、JFace        │
├─────────────────────────────────────────────┤
│ 1. 运行时/模块层                             │
│    Equinox（OSGi 实现）、Bundle、扩展注册表   │
└─────────────────────────────────────────────┘
```

关键事实：

1. **Eclipse IDE 本身就是一个 RCP 应用。**
   它的 Java 编辑器、Git 视图、调试器、Maven 集成，全都是插件。
2. **Eclipse 没有传统意义上的“一个巨大 main 方法”。**
   启动器先启动 OSGi 运行时，再根据 product/application ID 创建 Workbench。
3. **你开发的 RCP 应用，和 Eclipse IDE 用的是同一套底座。**
   区别只是：IDE 装的是 JDT/PDE/Git 等插件；你的产品装的是你自己的业务插件。

### 类比

把 Eclipse 想成一块**带插槽的主板**：

- Equinox/OSGi 是主板的供电和总线；
- Workbench 是机箱和面板；
- 插件是显卡、网卡、硬盘；
- 扩展点是插槽标准；
- Product 是最终贴牌组装出来的整机。

你不是在“改主板”，而是在“做板卡”，最后把板卡组装成自己的整机。

## 三、为什么一开始就是“开发插件”

因为 Eclipse 的扩展模型就是“**一切皆插件**”。

### 3.1 一个 RCP 应用由什么组成

最小的心智模型：

```text
你的业务插件（Bundle）
   ├─ MANIFEST.MF        声明依赖、导出包、Java 版本
   ├─ plugin.xml         向 3.x 扩展点注册视图/菜单/首选项
   └─ Application.e4xmi  描述 e4 的窗口、Part、菜单结构
        ↓
Feature（可选，把多个插件打成一组）
        ↓
Product（.product，定义应用 ID、启动画面、图标、包含哪些 Feature）
        ↓
p2 仓库 / 导出目录（最终可安装、可升级的产品）
```

即使你用“Eclipse 4 RCP Application”向导创建一个看起来“空白”的应用，它本质上也是一个插件项目：里面有 `MANIFEST.MF`、`Application.e4xmi`、`plugin.xml`。

### 3.2 为什么不能像普通 Java 程序那样写 `main`

普通 Java 桌面程序：

```java
public static void main(String[] args) {
    JFrame frame = new JFrame("Hello");
    frame.setVisible(true);
}
```

Eclipse RCP 不是这样：

- 窗口、菜单、工具栏、视图、编辑器、状态栏，都是平台创建的；
- 你的代码通过扩展点/应用模型“挂”进去；
- 平台负责生命周期、依赖注入、事件分发、主题、布局、持久化。

所以你要学的是“**如何向平台贡献功能**”，而不是“如何从零画一个窗口”。

### 3.3 “Run As > Eclipse Application”为什么又开了一个 Eclipse

这是新手最容易误会的地方。

- 第一个 Eclipse：**开发用的 IDE**（host），你在这里写代码；
- 第二个 Eclipse：**运行时实例**（runtime），它加载“目标平台 + 你的插件”，相当于你的应用。

它不是 bug，而是 RCP 的开发方式：

```text
开发 IDE
  │  编译你的 Bundle
  ▼
PDE 启动配置
  │  启动 Equinox + 目标平台 Bundle + 你的 Bundle
  ▼
运行时 Workbench（第二个 Eclipse 窗口）
  │  读取 plugin.xml / Application.e4xmi
  ▼
你的视图/菜单/Part 出现
```

这也解释了为什么“IDE 里能跑，导出后不能跑”：因为运行时实例和最终产品使用的**目标平台、插件集合、启动参数**可能不同。

## 四、五个必须分清的词

| 名词 | 一句话解释 | 类比 |
|---|---|---|
| **Bundle / Plugin** | OSGi 的模块单位，一个 JAR + `MANIFEST.MF` | 一张板卡 |
| **Extension / Extension Point** | 插件向平台注册功能的机制 | 插槽和插槽标准 |
| **Target Platform** | 你的插件编译/运行时依赖的那套 Eclipse Bundle | 你针对哪一代主板开发 |
| **Feature** | 一组插件的可安装集合，带版本 | 一个驱动包 |
| **Product** | 带品牌、图标、启动画面的最终应用 | 贴牌整机 |
| **p2** | Eclipse 的安装/更新/依赖解析机制 | 应用商店 + 安装器 |

再补充两个：

- **Fragment**：给宿主 Bundle 追加内容（平台相关 native 库、测试代码常用）。
- **Application / Product ID**：启动时告诉 Equinox“要跑哪个应用”。

## 五、OSGi 为什么重要

OSGi 是 Eclipse 的模块化基础。你以后遇到的很多“玄学问题”，根因都在这里。

### 5.1 Bundle 不是普通 JAR

一个 Bundle 的 `MANIFEST.MF` 里通常有：

```text
Bundle-SymbolicName: com.example.hello
Bundle-Version: 1.0.0.qualifier
Bundle-RequiredExecutionEnvironment: JavaSE-21
Bundle-Activator: com.example.hello.Activator
Bundle-ActivationPolicy: lazy

Export-Package: com.example.hello.api
Import-Package: org.eclipse.core.runtime, org.eclipse.jface.viewers
Require-Bundle: org.eclipse.ui
```

- `Bundle-SymbolicName`：全局唯一 ID。
- `Bundle-Version`：版本。
- `Bundle-RequiredExecutionEnvironment`（BREE）：最低 Java 级别。
- `Export-Package`：哪些包是公开 API。
- `Import-Package`：按“包”依赖别人。
- `Require-Bundle`：按“整个 Bundle”依赖别人。
- `Bundle-Activator`：Bundle 启动时的入口（能不用就不用）。
- `Bundle-ActivationPolicy: lazy`：有人真正用这个 Bundle 的类时才启动。

### 5.2 每个 Bundle 有自己的类加载器

这是 OSGi 和普通 classpath 最大的区别：

- 普通 Java：所有 JAR 丢进一个 classpath，谁都能看见谁，容易“JAR 地狱”。
- OSGi：每个 Bundle 一个类加载器，只有 `Export-Package` 的包才对别人可见。

好处：模块边界清晰、可以多版本共存。
坏处：**没导出/没导入就 `NoClassDefFoundError`**，而且编译期可能完全正常。

### 5.3 `Import-Package` 和 `Require-Bundle` 怎么选

| 方式               | 依赖粒度      | 优点                 | 缺点           |
| ---------------- | --------- | ------------------ | ------------ |
| `Import-Package` | 包         | 解耦、只依赖公开 API、可替换实现 | 要逐个列包，初学麻烦   |
| `Require-Bundle` | 整个 Bundle | 简单、直接              | 耦合紧、容易依赖内部实现 |

初学可以用 `Require-Bundle` 快速跑通；做正式产品时优先 `Import-Package`。

### 5.4 Bundle 生命周期

```text
INSTALLED → RESOLVED → STARTING → ACTIVE → STOPPING → UNINSTALLED
```

- **RESOLVED**：依赖都能找到，但还没启动。
- **ACTIVE**：已经启动，Activator 执行过。
- 启动失败常见原因：依赖缺失、版本不匹配、BREE 不匹配。

### 5.5 为什么会有“目标平台”

你的插件编译时，需要知道 `org.eclipse.ui`、`org.eclipse.jface` 这些类从哪里来。**Target Platform 就是这套“平台 SDK”**。

- 用 Running Platform：直接拿当前 IDE 的插件当依赖，简单但不稳定。
- 用 Target Definition（`.target`）：明确锁定 2026-06 更新站点，团队/CI 可复现。

正式项目一定要用 `.target`，否则“你机器上能编译，我机器上不行”。

## 六、PDE 是做什么的

PDE（Plug-in Development Environment）是“开发 Eclipse 插件的工具”，它本身也是 Eclipse 插件集合。

它提供：

- Plug-in 项目向导；
- `MANIFEST.MF` 编辑器；
- `plugin.xml` 扩展点编辑器；
- Target Platform 配置；
- Eclipse Application 启动配置；
- Plug-in Spy（看某个界面元素来自哪个插件）；
- Product/Feature 导出；
- PDE Error Log。

这也是为什么安装时选 **RCP 包**而不是普通 Java 包：RCP 包自带 PDE 和 e4 工具。

## 七、为什么要 JDK 21，为什么还要单独装 JDK

### 7.1 JRE 和 JDK 不是一回事

- **JRE**：只能运行 Java 程序。
- **JDK**：包含 JRE + 编译器（javac）+ 各种工具（jar、jlink、jpackage、jarsigner）。

Eclipse 安装包自带一个 JRE，所以“只运行 IDE”够了。但你要：

- 命令行编译（Tycho 需要 JDK）；
- 打包独立产品；
- 用 toolchains 指定编译 JDK；

所以还要单独装 JDK。

### 7.2 为什么是 21，不是 17 或 25

- Eclipse **2026-06** 的平台 Bundle 以 **Java 21** 为最低执行环境（BREE = JavaSE-21）。
- Eclipse **2026-09** 的 IDE 安装包要求 **Java 25**。
- 你选择 Java 21，所以配 2026-06，版本正好对齐。

如果你的产品要跑在 Java 17 上，就不能用 2026-06 的平台 Bundle 强行降级，而要用更老的 Eclipse 目标平台（例如 2024-03 一代）。

### 7.3 类文件版本

| Java | class 文件主版本 |
|---|---|
| 17 | 61 |
| 21 | 65 |
| 25 | 69 |

如果你用 JDK 21 编译出 class 65，却放到 Java 17 上运行，就会报：

```text
UnsupportedClassVersionError: class file version 65.0
```

这就是“JDK 版本 / BREE / 目标平台”必须对齐的原因。

### 7.4 为什么保留 JDK 17

- 维护老项目；
- 兼容旧目标平台；
- 用 `toolchains.xml` 让不同模块用不同 JDK 编译。

## 八、为什么要 Maven + Tycho

### 8.1 普通 Maven 不够用

普通 Maven 依赖长这样：

```xml
<dependency>
  <groupId>org.eclipse.jface</groupId>
  <artifactId>org.eclipse.jface</artifactId>
  <version>3.x.x</version>
</dependency>
```

但 Eclipse/OSGi 的依赖住在 **p2 仓库**里，用 `Bundle-SymbolicName` + `Bundle-Version` 标识，不是 Maven Central 的坐标。

Tycho 的作用：

- 让 Maven 能读 `.target` 文件和 p2 仓库；
- 解析 OSGi Bundle 依赖；
- 编译插件/Feature；
- 导出 Product；
- 生成 p2 仓库；
- 跑插件测试。

所以：

- **PDE**：日常开发、调试、看扩展点；
- **Maven + Tycho**：命令行、CI、可复现构建、正式交付。

两者不是替代关系，是配合关系。

### 8.2 为什么还要 settings.xml / toolchains.xml

- `settings.xml`：配置 Maven 镜像（本次用阿里云），加速 Maven Central 构件下载。
- `toolchains.xml`：告诉 Tycho“JDK 21 在哪、JDK 17 在哪”，按需选择编译器。
- `mvn21.cmd`：因为本机系统 `JAVA_HOME` 还是 17，用包装脚本强制 Maven 跑在 21 上。

## 九、为什么要 workspace、eclipse.ini、环境变量、快捷方式

### 9.1 Workspace 不是项目目录

Workspace 是 Eclipse 的“工作区容器”，里面有：

- 你的项目；
- `.metadata/`：IDE 的状态、首选项、历史、标记、日志；
- `.metadata/.log`：排错第一现场。

它不是 Eclipse 安装目录。分开的好处：

- 升级/重装 Eclipse 不会丢项目；
- 备份/迁移简单；
- 可以给不同项目建不同 workspace。

### 9.2 为什么路径不要有空格和中文

不是 Eclipse 一定不行，而是：

- 某些 native 工具、launcher、p2、Tycho 对空格/非 ASCII 路径兼容性差；
- 出错时错误信息往往很隐晦。

学习阶段直接用纯英文路径，能少踩一类坑。

### 9.3 eclipse.ini 是什么

Eclipse 启动器会读 `eclipse.ini`，它决定：

- 用哪个 JVM（`-vm`）；
- JVM 参数（`-Xmx4g`、编码、GC）；
- 启动哪个 product；
- OSGi 要求的最低 Java 版本。

`-vm` 必须写在 `-vmargs` 之前，因为它是给“启动器”的，不是给 JVM 的。写到后面就会被当成普通 JVM 参数，表现为启动失败或忽略。

### 9.4 环境变量为什么这么绕

- `JAVA_HOME`：很多工具（Maven/Gradle/Tomcat）用它找 JDK。
- `PATH`：决定命令解析顺序。
- Windows 的 PATH = 系统 PATH + 用户 PATH，系统部分在前。
- 本机系统 PATH 里 Oracle javapath 和 JDK 17 在前，所以直接敲 `java` 可能还是 17。

这不是安装失败，而是“命令解析顺序”问题。解决方案：

- Eclipse 用 `-vm` 固定；
- Maven 用 `mvn21.cmd` 固定；
- 需要时用绝对路径 `D:\Java21\bin\java`。

### 9.5 为什么用快捷方式/启动脚本

固定 `-data` 工作空间，避免每次启动都选错 workspace。

## 十、SWT、JFace、e4 分别是什么

### 10.1 SWT：原生控件层

- 直接调用操作系统控件（Windows 上是 Win32）；
- 外观原生、性能好；
- 需要手动 `dispose()` 颜色/字体/图片；
- 单 UI 线程，跨线程操作会 `Invalid thread access`。

SWT 是“砖块”。

### 10.2 JFace：MVC 封装层

- `TableViewer` / `TreeViewer` / `ComboViewer`；
- `ContentProvider` + `LabelProvider`；
- 向导、首选项、对话框、数据绑定、进度条。

JFace 是“预制墙板”，让你不用直接搬砖。

### 10.3 e4：应用模型 + 依赖注入

- UI 结构描述在 `Application.e4xmi`（EMF 模型）；
- `MPart`、`MPerspective`、`MWindow` 等模型元素；
- `@Inject`、`@Execute`、`@CanExecute`、`@Preference` 等注解；
- `IEclipseContext`、`EPartService`、`EEventBroker` 等服务；
- CSS 主题。

e4 是“装配图纸 + 依赖注入容器”。

### 10.4 为什么还要学 3.x 兼容层

很多企业老项目仍然使用：

- `ViewPart`；
- `plugin.xml` 扩展点；
- `ApplicationWorkbenchAdvisor`；
- `HandlerUtil`。

现代项目也可能“3.x + e4 混合”。所以两条线都要认识，但先学纯 e4，再回头看兼容层。

## 十一、为什么需要 Feature、Product、p2

### 11.1 三个层次

```text
Plugin（代码单元）
   ↓ 被包含
Feature（可安装的一组插件 + 版本）
   ↓ 被包含
Product（品牌、启动画面、图标、应用 ID、包含哪些 Feature）
   ↓ 导出
p2 仓库 / 安装目录（可安装、可升级）
```

- 只有一个插件也能跑，但正式产品通常用 Feature 组织。
- Product 决定“用户看到什么”：名称、图标、splash、About、默认透视。
- p2 负责“安装、更新、依赖解析”。

### 11.2 为什么不能直接复制 JAR

因为一个可运行的 RCP 产品还需要：

- 原生 launcher（`eclipse.exe`）；
- `eclipse.ini` / `configuration/config.ini`；
- Bundle 的安装布局；
- p2 元数据；
- 品牌资源；
- 正确的启动参数。

Product 导出/Tycho 会帮你生成这些。

## 十二、点击 Run 之后，到底发生了什么

以“新建一个带视图的插件”为例：

1. PDE 用 ECJ 编译你的 Bundle，按 `MANIFEST.MF` 计算依赖。
2. PDE 生成一个启动配置：目标平台 Bundle + 你的 Bundle + `-application` / `-product`。
3. 启动器启动 Equinox（OSGi 框架）。
4. Equinox 解析所有 Bundle：检查 `Import-Package` / `Require-Bundle` / 版本 / BREE。
5. 平台读取扩展注册表（`plugin.xml`）或 e4 应用模型（`Application.e4xmi`）。
6. Workbench 创建窗口、菜单、Perspective、Part。
7. 依赖注入把 `IEclipseContext`、服务、偏好设置注入你的类。
8. 你的 `@PostConstruct` 执行，SWT 控件被创建，窗口出现。
9. 关闭时 `@PreDestroy` 执行，资源释放，Bundle 停止。

一张图：

```text
你的 Bundle
  │ MANIFEST.MF / plugin.xml / Application.e4xmi
  ▼
PDE 启动配置
  ▼
Equinox OSGi 运行时  ←  Target Platform（2026-06 的 Bundle）
  ▼
Workbench / e4 应用模型
  ▼
SWT Shell + JFace Viewer
  ▼
你的界面
```

理解这条链路，你就知道每个报错大概出在哪一层：

- `NoClassDefFoundError` / `BundleException` → OSGi 依赖层；
- 视图没出现 → 扩展点/应用模型层；
- 布局错乱/资源泄漏 → SWT 层；
- 导出失败 → Feature/Product/p2 层；
- 启动就崩 → `eclipse.ini` / JDK 层。

## 十三、常见误解

| 误解 | 事实 |
|---|---|
| “Eclipse 就是一个编辑器” | Eclipse 是插件平台，IDE 只是它的一个产品 |
| “插件就是浏览器插件” | 这里的插件是 OSGi Bundle |
| “开发 RCP 要改 Eclipse 源码” | 不需要，你通过扩展点/应用模型扩展 |
| “Run 又开一个 Eclipse 是 bug” | 那是运行时实例，正常 |
| “Java 21 表示所有依赖都必须用 21 编译” | 平台 Bundle 有 BREE 下限；你的代码可以按目标级别编译 |
| “Workspace 就是项目文件夹” | Workspace 是容器，里面还有 `.metadata` |
| “插件装得越多越好” | 目标平台越小越稳定，按需安装 |
| “RCP 已经没人用了” | 企业工具、嵌入式 IDE、建模工具仍在用；但要按场景选型 |
| “Maven 可以完全替代 PDE” | 开发调试靠 PDE，构建交付靠 Tycho，二者配合 |
| “目标平台可有可无” | 正式项目必须有，否则构建不可复现 |

## 十四、为什么学习顺序是“Java → OSGi/PDE → SWT/JFace → e4 → 产品化”

因为每一层都依赖前一层：

```text
产品化（Feature/Product/p2/Tycho）
   ↑ 需要
e4（应用模型/DI/命令/事件）
   ↑ 需要
JFace / SWT（界面）
   ↑ 需要
OSGi / PDE（模块与扩展）
   ↑ 需要
Java（语言与工程能力）
```

如果跳过 OSGi：

- 不知道为什么视图不显示；
- 不知道为什么编译过、运行报 `NoClassDefFoundError`；
- 不知道为什么换个 Eclipse 版本就跑不起来。

如果跳过 SWT：

- 布局一塌糊涂；
- 资源泄漏；
- UI 线程阻塞/崩溃。

如果跳过 e4：

- 看不懂现代 RCP 项目的 `Application.e4xmi`；
- 不会用 DI/命令/事件。

如果跳过产品化：

- 代码能跑，但交付不了；
- 不会做安装包、更新站点、CI。

## 十六、装好的东西分别对应什么

| 安装项 | 本质 | 不装会怎样 |
|---|---|---|
| JDK 21 | Java 运行时 + 编译器 | Eclipse 无法启动；Tycho 无法编译 |
| Eclipse RCP 包 | 平台 + IDE + PDE + e4 工具 | 没有插件开发环境 |
| Maven | 构建工具 | 无法命令行/CI 构建 |
| Tycho | Maven 插件（随 pom 引入） | Maven 不认识 p2/OSGi 依赖 |
| Git | 版本控制 | 无法管理代码、回退、协作 |
| 7-Zip | 解压工具 | 无法解压 Eclipse/JDK zip |
| `settings.xml` | Maven 镜像配置 | 下载慢 |
| `toolchains.xml` | 多 JDK 选择 | 编译 JDK 可能不对 |
| `mvn21.cmd` | 固定 JDK 21 的 Maven 包装 | 可能用 JDK 17 构建，class 版本不对 |
| `eclipse.ini` | Eclipse 启动参数 | 可能用错 JVM、内存不足、编码错 |
| Workspace | 项目容器 + `.metadata` | IDE 状态混乱 |
| 快捷方式/启动脚本 | 固定工作空间 | 每次启动选错 workspace |

## 十七、你现在应该建立的三个直觉

1. **看到“视图/菜单/编辑器”时，先问：它是由哪个插件、通过哪个扩展点贡献的？**
2. **看到“依赖/找不到类/版本冲突”时，先问：目标平台里有没有这个 Bundle？版本/BREE 对不对？**
3. **看到“导出后不能运行”时，先问：产品里包含的 Feature/Bundle 和运行时目标平台是否一致？**

这三问能覆盖 RCP 开发 80% 的排错场景。

## 十八、下一步

概念有了，再回到 [03-12周行动计划](03-12周行动计划.md) 的第 1 周：

1. 打开 Eclipse，设置 UTF-8、JDK 21；
2. 新建 `com.example.hello` 插件；
3. `Run As > Eclipse Application`；
4. 观察第二个 Eclipse 窗口，找到你的视图；
